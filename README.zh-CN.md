F-Droid 已经停止在 GitHub 发布客户端 APK。这个仓库，就是为了把这道门继续留着。

我是一名来自中国的中学生，想坦诚地说一句：我的技术还很有限。我没法给 F-Droid 的代码打补丁，也加不了新功能；自由软件的世界很大，里面有很多东西，我目前还看得懂、但暂时做不来。但我真的爱上了开源所代表的东西——软件可以是自由的、透明的，可以由一群素不相识的人，仅仅因为“这件事是对的”，就彼此帮助、一起把它做出来。正是这个想法，让我也想尽自己一点微薄的力量，把些什么回馈回去。

我能做的，是这一段：F-Droid 的大本营在 GitLab，他们已经不再往 GitHub 发布新版本了。可当我所在的网络环境连官网或 GitLab 都不稳定时——说实话，这种事经常发生——大家就拿不到最新的客户端。可要是连应用商店本身都装不上，又怎么有机会遇见它背后那成千上万的自由软件呢？我觉得这不该是这样，尤其对和我一样的人：学生、好奇的小孩、任何刚刚起步、正想学着点什么的人。所以这个仓库就是我的回答：每一次官方发布新版，我都会把 F-Droid 官方构建并签名的安卓客户端原样镜像到这里——**不修改、不重打包，永远如此**。你可以把它当成多开的一扇侧门：正门挤不进来的时候，至少还有一个地方能进。

## 每次发布里有什么

每次官方客户端更新，我都会上传**两个文件，一次不落：**

- `F-Droid_<version>.apk` —— 官方客户端，原封不动
- `F-Droid_<version>.apk.sha256.txt` —— 一个纯文本文件，里面写着**这个 APK 的文件哈希**

那个 `.sha256.txt` 就是个文本文件。在任何一部手机上点开，你都会看到一行：这次构建的 SHA-256。我特意保留 `.txt` 后缀——不玩去掉扩展名那套花活，就是为了它在什么设备上都能直接打开，新手也看得懂。

## 关于那个 `.sha256.txt`（这一段请一定看）

**`.txt` 里的哈希，是这个 APK 文件自己的哈希。它不是签名证书的指纹。这是两码事，千万别混。**

- 每次构建出来的 APK 都不一样，所以**这个哈希每个版本都会变**。这很正常——新版本，新哈希。
- 它只能证明：文件在下载途中没有损坏。**它证明不了这个包是谁签的。**
- 要确认它真的是 F-Droid 的官方包，得**另外**校验证书（看下一节）。

电脑上快速校验：
`sha256sum -c F-Droid_*.apk.sha256.txt`

手机上没有 `sha256sum`？那就直接打开 `.txt`，把里面的哈希和发布页面上显示的值对一眼。对得上，说明文件完整没坏。

## 签名也请验一下（这一步别跳）

| | 文件哈希（那个 `.txt`） | 证书指纹 |
|---|---|---|
| 证明什么 | 下载的文件完整没坏 | 这个包真的是 F-Droid 发的 |
| 会不会变 | **每个版本都变** | **永远不变**（有效期至 2037 年） |
| 怎么验 | `sha256sum -c`，或肉眼比 | `keytool -printcert -jarfile` |

要认的证书指纹，**永远**是这一个：

    43238d512c1e5eb2d6569f4a3afbf5523418b82e0a3ed1552770abb9a9c9ccab

（F-Droid 官方公布的就是这枚长期签名证书，有效期到 2037 年。）

- **APK 哈希对不上？** 正常，每个版本都有自己的哈希。
- **证书对不上？** 停下。**千万别装**——不管文件名多像、文件哈希多“漂亮”，都没用。

Linux / macOS 上：`keytool -printcert -jarfile F-Droid_*.apk` 打印出来的应该是同一个证书值。安卓系统本身也会拒绝任何签名不匹配的后续更新，所以**第一次装对**，后面每一次更新才都安全。
